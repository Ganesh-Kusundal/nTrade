The module exposes two interchangeable execution targets through a single `submit(intent)` interface: `BrokerExecution` (live, delegates to a `BrokerAdapter` via `instrument.order.place`) and `SimulatedExecution` (deterministic, fills against instrument quotes). Both are registered by name in `ExecutionRouter`, which dispatches an `OrderIntentEvent` to the target matching the intent's strategy or a configured `default`. `BrokerExecution` maintains an in-memory `_open` dict of pending orders, publishes `OrderAcceptedEvent` immediately on submission, and advances lifecycle events (`OrderUpdatedEvent`, `OrderFilledEvent`, `OrderRejectedEvent`, `OrderTimeoutEvent`) through `poll()`, with crash recovery via `restore_open()` from persisted deltas. `SimulatedExecution` computes fill prices through pluggable `SlippageModel` implementations, applies `CommissionModel` and `IndianStatutoryCosts` (with delivery-detection for overnight equity), and emits `OrderAcceptedEvent`/`OrderFilledEvent` synchronously. `costs.py` defines the abstract `SlippageModel`/`CommissionModel` interfaces plus concrete strategies and the full Indian statutory schedule (STT, exchange charges, SEBI fee, GST, stamp duty). `retry.py` provides a frozen `RetryPolicy` dataclass (exponential backoff + jitter) and a thread-safe token-bucket `RateLimiter`, both stdlib-only for the hot path. Dependency direction is one-way: router → execution targets → cost models; targets depend on `ntrade.events.order` and `ntrade.domain.*` but never on each other, preserving the zero-parity invariant.
